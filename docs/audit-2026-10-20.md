## Findings

### 1. P1 — A job's old records can reuse overwritten or truncated output

**Location:** [steps.py:112](../src/videoforge/core/pipeline/steps.py#L112),
[reuse.py:69](../src/videoforge/core/pipeline/reuse.py#L69).

`_reusable()` compares the command/input fingerprint and checks that output files exist.
It does not check that those files are still the ones the successful run produced.
`reuse_offers()` also trusts a job's own record even when `finished_files()` rejects the
current file's size/mtime.

This matters because variants of the same source share a work folder and output names.
Job B can overwrite Job A's audio output, or leave it incomplete after cancellation.
Rerunning A can then reuse B's file as A's completed result. A video with the same script
but different encoder settings can encounter the same problem.

**Reproduction:** finish a step, replace its output with `truncated`, then rerun with its
original records. The encode executes only once; the rerun leaves `truncated` untouched,
even though `finished_files()` correctly returns an empty result.

**Fix direction:** validate output identity as well as input identity before offering or
automatically reusing a step. Store and verify output size/mtime and reconcile the
work-folder record with the job's record. Invalidate completion before replacing files.
Apply the same checks to the user-selected reuse path.

### 2. P2 — VFR muxing applies different time origins to video and other tracks

**Location:** [mux.py:164](../src/videoforge/core/execute/mux.py#L164),
[mux.py:227](../src/videoforge/core/execute/mux.py#L227),
[build.py:510](../src/videoforge/core/pipeline/build.py#L510).

The extracted VFR timestamps retain the source video's starting offset. The mux applies
them unchanged to the encode, while shifting the source audio and subtitles by
`-video.start_ms`, assuming that the encoded video starts at zero.

**Real reproduction:** create a VFR MKV whose video starts at 500 ms and whose subtitle
starts at 1,200 ms. The resulting video still starts at 500 ms, but the subtitle moves
to 700 ms. Its position relative to the video changes from 700 ms to 200 ms: **500 ms early**.
Negative audio timestamps also cause leading audio packets to be dropped.

The notes identified a possible TS timing problem. This reproduction demonstrates the
same inconsistency in an MKV source too.

**Fix direction:** normalize the video timestamps to the encode's zero origin, or retain
the source origin consistently for every track. Test both copied and encoded audio.

### 3. P2 — Burned subtitles ignore the source video's starting offset

**Location:** [burn.py:76](../src/videoforge/core/video/burn.py#L76),
[build.py:181](../src/videoforge/core/pipeline/build.py#L181).

The extracted subtitle file retains container timestamps, but the generated SubText call
renders them against a clip beginning at its first decoded video frame. No adjustment
for the source video's nonzero start is made.

**Real reproduction:** a constant-rate source has video starting at 500 ms and a cue at
1,200 ms. Relative to its first frame, that cue belongs at 700 ms, or frame 18 at 25 fps.
SubText shows no text at frames 18 or 29, and shows it at frame 30: **500 ms late**.
This was checked independently of the VFR reproduction.

**Fix direction:** move extracted source subtitles onto the clip's time origin before
rendering. Preserve standalone subtitle files' own timing unless they are known extracts.
Keep preview and encode on the same corrected path.

### 4. P2 — Editing an external burned subtitle does not invalidate the video

**Location:** [build.py:297](../src/videoforge/core/pipeline/build.py#L297).

Video steps fingerprint the generated script, source, and optional qpfile/metadata.
They omit the external subtitle file consumed by `core.sub.TextFile` / `ImageFile`.
Editing the file in place leaves the script text and video fingerprint unchanged.

**Reproduction:** replace the text and size of a selected external SRT. The video
fingerprint is identical before and after; its input list contains only `video.vpy`
and the source MKV. A normal rerun can reuse the video containing the old subtitles.

**Fix direction:** include the burn input in the video dependencies and relevant preview
cache keys. For VobSub, include both the `.idx` and `.sub` files.

### 5. P2 — Quoted extra arguments reach tools with literal quote characters

**Location:** [mux.py:388](../src/videoforge/core/execute/mux.py#L388),
[encoders.py:225](../src/videoforge/core/video/encoders.py#L225),
[audio.py:699](../src/videoforge/core/execute/audio.py#L699).
The VP8/VP9 and SVT-AV1 builders use the same parsing pattern.

`shlex.split(..., posix=False)` preserves enclosing quotes. The result is then passed
as an argv list to `Popen`, so those quotes become part of the argument rather than
shell grouping syntax.

**Real child-process reproduction:**

```text
Typed:     --chapters "C:\My Clips\chapters.txt"
Received:  ['--chapters', '"C:\\My Clips\\chapters.txt"']
Expected:  ['--chapters', 'C:\\My Clips\\chapters.txt']
```

Paths can fail to open; quoted numeric or compound encoder values can be rejected.
Titles can acquire unwanted literal quotes.

**Fix direction:** use one tested argv parser for all extra-argument fields. It must
remove grouping quotes while preserving Windows backslashes and embedded quotes.
Simply switching to default POSIX splitting can damage unquoted Windows paths.
Python documents the non-POSIX quoting behavior in its
[shlex parsing rules](https://docs.python.org/3/library/shlex.html#parsing-rules).

### 6. P2 — IVF container color metadata ignores encoder overrides

**Location:** [build.py:554](../src/videoforge/core/pipeline/build.py#L554).

The encoder receives source color defaults followed by user overrides, but the mux
constructs its color tags directly from `video.color`. It never resolves the final
encoder settings. This affects the VP8/VP9 and SVT-AV1 container-tagging path.

**Reproduction:** a BT.709 limited-range source with SVT overrides
`color-primaries=9` and `color-range=1` gives the encoder BT.2020/full as its final
arguments. The MKV command nevertheless explicitly writes primaries 1 (BT.709)
and container range 1 (limited). The stream and container declarations disagree.
The MP4 path receives the same source-derived tag object.

**Fix direction:** derive one effective output color description after applying settings,
and use it for both encoder and container. Avoid writing stale source tags when an
override cannot be interpreted. Validate the muxed metadata.

### 7. P2 — Direct MKV subtitle import loses the final cue's duration with installed MP4Box

**Location:** [mux.py:378](../src/videoforge/core/execute/mux.py#L378).

Source subtitles are imported directly with `source.mkv#trackID=...`.
With GPAC 2.4 on this machine, an SRT track imported this way loses its final cue's
duration. VideoForge's validation checks the track format/flags, not cue durations.

**Real reproduction:** an MKV contains cues at 1.2–2.0 seconds and 2.4–2.8 seconds.
After the generated MP4Box command, decoding the MP4 subtitle track yields
1.2–2.0 and **2.4–2.4** seconds. Importing the original SRT directly into MP4Box
preserves both intervals. A one-cue test likewise produced a zero-duration cue.

This is an upstream importer behavior exposed by VideoForge's integration, not a
claim that every GPAC version has this defect.

**Fix direction:** extract text subtitles to a supported standalone format before MP4
import, with explicit timing handling; alternatively enforce and test a tool version
that preserves the durations. StaxRip's subtitle-file import path is a useful reference.

## Reference comparison

The inspected implementation agrees with StaxRip's basic approach in these areas:

- Target bitrate: subtract non-video data and per-frame container overhead, then divide
  the remaining bits by duration. VideoForge's full subtitle/attachment accounting is
  an intentional difference, not a finding.
  [StaxRip Calc](https://github.com/staxrip/staxrip/blob/2283bfd0a892542feecdbb813b1fcda144f7d610/Source/General/Misc.vb#L125).
- Script-derived raw-video frame rate and `mkvextract timestamps_v2` / `--timestamps`
  for VFR. Sharing this approach does not resolve VideoForge's origin mismatch above.
  [StaxRip mux](https://github.com/staxrip/staxrip/blob/2283bfd0a892542feecdbb813b1fcda144f7d610/Source/General/Muxer.vb#L768),
  [MKVToolNix timestamp documentation](https://mkvtoolnix.download/doc/mkvmerge.html#mkvmerge.external_timestamp_files).
- SVT-AV1 frame limits, pass/stats arguments and rate-control construction; x265 HDR
  metadata and profile 5 preservation. The documented SVT undershoot adjustment is an
  intentional divergence. Unsupported DV 8.4 and cuts remain documented scope limits.
  [StaxRip SVT-AV1](https://github.com/staxrip/staxrip/blob/2283bfd0a892542feecdbb813b1fcda144f7d610/Source/Encoding/SvtAv1Enc.vb#L1464),
  [StaxRip x265](https://github.com/staxrip/staxrip/blob/2283bfd0a892542feecdbb813b1fcda144f7d610/Source/Encoding/x265Enc.vb#L225).
- StaxRip imports selected subtitle files into MP4, giving a reference for avoiding
  the direct MKV importer problem.
  [StaxRip MP4 subtitles](https://github.com/staxrip/staxrip/blob/2283bfd0a892542feecdbb813b1fcda144f7d610/Source/General/Muxer.vb#L380).
